# 单位端资源承租、续租、退租小程序设计

## 目标与范围

将 `creek-qiankun/src/routes/Biz/ziyuanguanli` 的单位端承租、续租、退租申请能力移植到 `creek-microapp-report` 的资源管理分包。面向 `userType === 1` 的单位用户。保留小程序现有的资源详情、租赁记录与创建资源能力，并按已确认的设计图统一台账入口。

本次支持单资源及多资源申请：从资源详情进入时预选当前资源；从台账操作菜单进入时先选择适用资源，可选择多条。三种操作分别调用现有单位端 `*Apply` 接口。系统端直生效操作及审批中心本身不在本次范围内。

## 入口与页面流

资源台账右下角保留现有悬浮按钮。点击后显示底部操作弹窗，顺序为「承租资源」「续租」「退租」「创建资源」。前 3 项进入对应的资源选择页，确认选择后进入申请页；「创建资源」进入现有 `resource-save` 页面。关闭弹窗回到台账，不改变查询或滚动位置。

资源卡片进入详情页。详情页的「租赁」按钮按资源状态和单位身份显示适用操作；选择后预选当前资源并进入同一申请页。台账与详情使用同一套操作规则和申请组件，提交结果保持一致。

资源选择页显示资源编号、名称、状态、分类、面积、位置与当前承租结束日期。承租只允许选择未承租资源（`status === 0`）。续租、退租允许选择已承租或已到期资源（`status === 1 || status === 4`），且当前单位必须是所有者或承租方。资源选择跨分页保留，切换操作清空旧选择。选择不适用资源时说明原因，不将其提交。

## 三类申请

### 承租

复用现有 `resource-lease` 页面和表单字段：承租方、申请人、承租单位性质、使用方式、实际使用方、承租开始与结束日期、消防安全责任人与管理人及电话、附件。页面从固定单资源扩展为 `applyRooms` 列表，支持增删所选资源。提交前校验必填、电话格式、开始日期不晚于结束日期，以及至少一条适用资源。

### 续租

页面内容与行为以 Web 单位端 `ResourceRenewal/ResourceRenewalForm.tsx` 为参照，将其弹窗改为小程序独立页面。顶部显示 Web 中的身份生效提示；所选资源表格改为纵向资源卡，逐条展示资源编号、名称、当前到期日期与资源角色。表单保留必填「续租结束日期」、可选多附件以及「取消」「提交申请」。提交 `applyRooms`、`rentEndAt` 与附件。日期按本地日期的 `23:59:59.000` 转换为毫秒时间戳。若列表缺失当前到期日期，页面显示「--」，不自行推断到期时间；服务端负责最终日期规则校验。

### 退租

页面内容与行为以 Web 单位端 `ResourceTermination/index.tsx` 为参照，将其弹窗改为小程序独立页面。顶部显示 Web 中的身份生效提示；所选资源表格改为纵向资源卡，逐条展示资源编号、名称、当前承租结束日期、资源角色与大功率电器状态。表单保留必填「退租日期」、可选多附件以及「取消」「提交申请」。提交 `applyRooms`、`rentNotAt` 与附件。退租日期按本地日期的 `23:59:59.000` 转换为毫秒时间戳。

进入退租流程时读取 `/api/data/v2/roomManage/roomConfigHighpowerblock`。若 `enabled` 为真，任一所选资源的 `hasPowerEquipment` 为真，则阻止提交并指出受阻资源。配置读取失败时显示错误并允许重试，不在配置未知时放行。小程序资源类型需要显式接收列表接口返回的 `hasPowerEquipment`；若缺失该字段，查询该资源现有的大功率电器统计 `inUseCount` 作为回退。两种来源均不可用时提示数据不足并阻止提交。

## 接口与数据约定

- 承租：`POST /api/data/v2/roomManage/roomRentApply`，沿用现有 `submitLease('lease', ...)`，补齐多资源及日期转换。
- 续租：`POST /api/data/v2/roomManage/roomRenewApply`，提交 `applyRooms`、`rentEndAt`、可选 `accessory`。
- 退租：`POST /api/data/v2/roomManage/roomReturnApply`，提交 `applyRooms`、`rentNotAt`、可选 `accessory`。
- 资源选择：沿用 `roomQuery`，承租用 `status: 0` 和 PC 的 `scene: 'rentChoose'`；续租、退租用现有列表查询与前端身份校验。提交前重新核对所选资源的当前状态。
- `applyRooms` 的每项包含 `roomId`、`roomNo`、字符串形式的 `sourceType` 与 `businessType`、数值形式的 `buildingArea`、由建筑/楼层/区域组成的 `address`。
- 附件统一映射为 `{ fileName, filePath }[]`，保留已上传文件。请求失败后保留表单和选择，显示服务端 `msg`；提交中禁止重复点击。

小程序现有 `LeaseFormValues` 仅约束 `roomId`，需要替换为三类明确的请求类型和纯转换函数，避免把页面表单值原样传给接口。承租日期分别规范到开始日 `00:00:00.000`、结束日 `23:59:59.000`。

## 状态与反馈

申请成功显示操作对应的成功提示，返回资源台账或详情并刷新列表、详情、统计与租赁记录。单位端续租、退租为申请流程，页面不预判审批结果；实际状态以刷新后的接口数据为准。页面返回、附件上传失败、配置读取失败及资源状态变化均应有明确提示和重试路径。

## 实施边界

建议按以下顺序开发和验收：

1. 抽出操作资格、资源映射、日期和附件转换，配契约测试。
2. 改造悬浮按钮底部菜单与资源选择流程，保留现有创建资源跳转。
3. 扩展承租申请页为多资源；新增续租、退租申请页及退租联锁。
4. 接通详情页的单资源入口、成功刷新与租赁记录，完成微信小程序构建和交互检查。

重点验收 `status 0/1/4`、所有者/承租方/使用方身份、跨页多选、日期边界、附件、退租联锁与接口失败保留表单。资源接口和联锁接口的字段契约以 PC 当前代码为依据，联调时若实际响应不同，应先确认后端契约再调整映射。
